用两个门槛判断成功

已有 Cookie 池时可以直接创建采集任务；只有需要补充新会话时才执行 Cookie 获取。服务启动、请求结束都不是业务成功，最终以 Cookie 容量和持久化结果为准。

01CONFIG加载运行配置

复制 .env.example 为 .env。Cookie、Redis 和代理秘密只由运行环境注入，不在页面中填写。

02PREFLIGHT检查服务与资源

启动 serve 后检查 health、capabilities 和 cookie-pools。目标任务类型、结果去向与 Cookie 来源必须可用。

03SESSION确认 Cookie 就绪

池内已有健康 Cookie 可跳过获取。新获取只有 satisfied=true 且 available_after ≥ requested 才通过。

04MISSION创建真实任务

在上方选择任务类型、站点、邮编和真实输入。默认服务内置 Worker，会自动执行、重试并保存逐项断点。

05EVIDENCE核对状态与结果

打开任务详情查看结果、事件、失败码和证据哈希。部分成功必须继续检查失败输入，不能只看进度条。

GATE 01Cookie Gate
池内存在可用会话

已有池可直接通过；生产新 Cookie 时，必须满足 available_after ≥ requested。created=0 可能表示原有容量已足够，但 satisfied=false 一定未通过。

GATE 02Result Gate
状态与持久化结果同时成立

succeeded 且结果数大于 0 才算全部完成；partial 表示结果可用但仍有失败项；failed 或零结果不能进入下游。

proxy_acquisition_failed

补充健康代理或等待隔离结束，不静默改为直连

Amazon 风控或验证码；降低频率并更换健康出口

页面形态或会话未就绪；检查站点、出口地区和拦截页
address_not_applied
邮编未生效；核对站点/邮编并保持同一代理会话
network_error
检查连接和超时，随后使用重试与断点恢复
